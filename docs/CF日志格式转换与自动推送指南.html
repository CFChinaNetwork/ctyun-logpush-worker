概述
🎯

目标

将 Cloudflare 边缘访问日志从 Logpush 的 JSON 格式转换为 CDN 伙伴的 145 字段格式，并近实时推送到客户的日志接收端。

🏗️

技术栈

100% Cloudflare 原生：Logpush + R2 + Queues + Workers。无服务器、无运维、按需自动扩容。

📋

日志格式

145 字段，以 \u0001 分隔的纯文本；正文 gzip 压缩；通过 MD5 URL 签名鉴权。

⚡

端到端时延

约 1–2 分钟（主要由 Logpush 约 1 分钟的攒批周期决定）。

使用到的 Cloudflare 服务

服务作用Dashboard 位置
Logpush把边缘 HTTP 请求日志导出到 R2（约 1 分钟一批，gzip ndjson）域名 → Analytics & Logs → Logpush
R2 对象存储存放原始日志文件与处理后的临时批次文件Dashboard → R2 Object Storage
R2 事件通知每个新写入的原始日志对象触发一条 Queue 消息R2 桶 → Settings → Event Notifications
Queues解耦解析与发送两段；at-least-once 投递，自动重试 + 死信队列Dashboard → Workers & Pages → Queues
Workers同一脚本三种角色：Parser、Sender、DLQ 重驱动通过 wrangler deploy 或 GitHub Actions 部署

架构

整条管线全程事件驱动。同一个 Worker 脚本消费全部 4 个队列：parse-queue（Parser）、send-queue（Sender）、parse-dlq / send-dlq（DLQ 重驱动）。下图标注了每一步对应的 wrangler.toml 参数。

工作原理

流式、定额解析

原始文件通过 DecompressionStream 边读边逐行转换，永不整文件载入内存。每攒满一批（BATCH_SIZE = 2000 行）即写入 R2 并入队 —— 峰值内存只受批大小限制，与文件大小无关。单次 invocation 内由小并发池（PARSE_PARALLELISM）并行解析多个文件；max_batch_size 必须 ≥ 该值。

单次读空闲超时

每次 R2 读取带一个空闲超时（PARSE_READ_IDLE_TIMEOUT_MS，默认 45s）。读卡死时中断、且只重试这一个文件，单个卡住的对象不会堵塞整条队列。由于是“单次读空闲”口径（而非整文件总时限），同一个值对任意文件大小都安全 —— 健康的大文件持续出块，永不触发。

幂等投递（接收端无需去重）

队列投递是 at-least-once。Parser 以确定性 key 写每个批次（processed/<safeKey>-<index>.txt）；Sender 成功 POST 后写 .done 标记。任何重新处理时，已有 .done 的批次直接跳过，因此一个批次绝不会被 POST 两次。源级 .done 还能让 Parser 跳过已完整处理过的整个文件。接收端无需自行去重。

死信自愈

主队列重试至多 5 次后转入死信队列。同一个 Worker 消费 parse-dlq / send-dlq，按指数退避 + 抖动把死信回灌到源队列。瞬时故障自动恢复 —— 无需告警、无需人工排空。（回灌同样依赖确定性 key + .done 标记，绝不产生重复发送。）

流式、chunked 发送

Sender 以 R2 对象 → gzip → fetch body 流式发送，单请求内存占用很小。请求使用 HTTP/1.1 Transfer-Encoding: chunked（无 Content-Length）。客户接收端必须支持 chunked 请求体；返回 400 / 411 / 415 即表示不支持。每次 POST 受 SEND_FETCH_TIMEOUT_MS（默认 30s）约束，接收端卡住即中断重试。单次 invocation 内由小并发池（SEND_PARALLELISM）并行发送多个批次，多个 invocation 也在 autoscaler 下并发。

CDN 节点国家（第 45 字段）

该格式要求填 CDN 节点所在国家（非客户端国家）。EdgeColoCode（IATA 机场三字码，如 NRT=东京）通过内置映射表转为 ISO 3166-1 两字码；为空或未命中时回退为 SG。

MD5 鉴权

Workers 的 SubtleCrypto 不支持 MD5，故内置了纯 JS 的 RFC 1321 实现。URL 签名为 MD5({uri}-{ts}-{rand}-{privateKey})，以 auth_key={ts}-{rand}-{md5} 形式附在 URL 上。

时间戳与 Content-Length

Parser 自动识别 EdgeStartTimestamp 的三种格式（Unix 秒、Unix 毫秒、RFC 3339）；建议 Logpush 配置 timestamp_format = unix。第 21 字段（sent_http_content_length）在配置了 Logpush Custom Fields 时取自 ResponseHeaders['content-length']（可选，见“部署”）；否则输出 -。

可靠性模型

场景行为恢复
接收端临时不可用send-queue 至多重试 5 次，每次间隔一段延迟自动；R2 文件在确认投递前一直保留
接收端单个请求卡住单次 POST 超时 SEND_FETCH_TIMEOUT_MS（默认 30s）中断，回退为队列重试自动；单个 invocation 不会撑满 15 分钟消费上限
某文件 R2 读卡死单次读空闲超时（PARSE_READ_IDLE_TIMEOUT_MS，45s）中断并只重试该文件自动；卡住的对象不堵塞其余队列
畸形日志行逐行捕获错误、跳过该行、批次继续记录错误计数；文件级处理仍成功
Parser/Sender 处理某文件/批次失败队列重试 5 次后转入对应 DLQ自动 —— 见下一行
消息进入 DLQ同一 Worker 按指数退避 + 抖动回灌源队列全自动自愈；无需人工排空、不丢数据
队列重复投递已有 .done 标记（或临时文件已删）→ 静默跳过由确定性 key + .done 标记收敛幂等

部署
前置条件：本地安装 Node.js v18+ 与 Wrangler CLI；一个范围限定到目标账号、具备 Workers Scripts:Edit、Workers R2 Storage:Edit、Workers Queue:Edit 权限的 Cloudflare API Token。并从日志伙伴处获取：接收端 URL、鉴权私钥、目标 URI 路径。
本模板每个域名部署一份。只需替换 wrangler.toml 中标注 【按域名修改 / 按域名必填】 的项，见下方配置清单。
1

创建 R2 桶

Dashboard → R2 Object Storage → Create bucket

  • 名称：<domain>-com（须与 bucket_name 及 [vars].R2_BUCKET_NAME 一致）
  • 位置：Automatic
2

创建队列

Dashboard → Workers & Pages → Queues → Create queue，创建全部 4 个：

队列用途
parse-queue-<domain>每个新 R2 文件触发 Parser
send-queue-<domain>每个处理后批次触发 Sender
parse-dlq-<domain>解析死信 —— 被自动消费并回灌 parse-queue
send-dlq-<domain>发送死信 —— 被自动消费并回灌 send-queue
3

配置 R2 事件通知

R2 → <domain>-com → Settings → Event Notifications → Add notification

  • 事件类型：object-create
  • 队列：parse-queue-<domain>
  • 前缀：logs/（必填 —— 不要对整桶通知）
  • 后缀（可选）：.gz
4

设置 Worker Secrets

# 接收端（base URL，结尾不带斜杠）
wrangler secret put CTYUN_ENDPOINT

# 鉴权私钥
wrangler secret put CTYUN_PRIVATE_KEY

# 目标 URI 路径（如 /logpost/yourpath）
wrangler secret put CTYUN_URI_EDGE
Secret 设置一次即持久保存在 Cloudflare，后续部署无需重新上传。
5

部署

wrangler deploy        # 或：push 到 main → GitHub Actions 自动部署
输出应确认 parse-queue / send-queue 的 producer 与 consumer 绑定，以及一个新的 Version ID。
6

配置 Logpush 任务

Dashboard → [目标域名] → Analytics & Logs → Logpush → Create a Logpush job

  1. 目标：R2  ·  桶：<domain>-com  ·  路径前缀：logs/{DATE}/
  2. 数据集：HTTP requests
  3. 字段：全选（Worker 对缺失字段有兜底）
  4. 时间戳格式：Unix  ·  采样率：1（100%）
6b

启用 Content-Length 记录 — 可选

若要让第 21 字段取真实的 Content-Length 响应头，需通过 API 配置 Logpush Custom Fields（一次性的 zone 级设置，Dashboard UI 无法配置）：新增一个 http_log_custom_fields ruleset 抓取 content-length，并把 ResponseHeaders 加入 Logpush 任务的字段列表。不配置时，第 21 字段输出 -。

7

端到端验证

等约 2 分钟后检查：

  1. R2：<domain>-com/logs/ 出现 .log.gz 文件
  2. 队列：parse-queue / send-queue 的 “Messages Processed” 在增长；DLQ 接近 0
  3. Worker 日志：wrangler tail
# 预期（LOG_LEVEL=info）
[INFO] Parsing: logs/20260328/xxx.log.gz
[INFO] Done: logs/20260328/xxx.log.gz | lines=73 batches=1 errors=0 ...
[INFO] Sent 73 ... → HTTP 200 | processed/xxx.txt
发送返回 401/403 → 检查 CTYUN_PRIVATE_KEY。   返回 404 → 检查 CTYUN_URI_EDGE。

配置

按域名修改清单 — 每次部署只需改这些

wrangler.toml 中改为
name<domain>-com-log
account_id该域名所在的 Cloudflare Account ID
R2 bucket_name + [vars].R2_BUCKET_NAME<domain>-com（两处一致）
队列名 —— 2 个 producer、4 个 consumer，以及 4 个 [vars] 的 *_QUEUE_NAME / *_DLQ_NAMEparse-queue-<domain>、send-queue-<domain>、parse-dlq-<domain>、send-dlq-<domain>（所有引用保持一致）
[vars].FIELD11_SERVER_IP必填。该域名的 anycast/解析 IP（如 172.65.90.64），写入第 11 字段 server_ip；留空则输出 -。

其余项均有合理默认，通常只改上表内容。

运维

健康指标

指标健康异常时
R2 logs/每约 1 分钟出现新 .gz 文件检查 Logpush 任务是否启用
parse-queue / send-queue backlog低且稳定持续增长 → 查 Worker 日志 / 接收端可用性
parse-dlq / send-dlq接近 0（自动排空）只有持续增长的 DLQ 才需关注（不可处理的文件或接收端宕机）
R2 processed/不堆积堆积 → Sender 未消费；查 Worker 日志

指标解读

信号含义动作
backlog 低 + lag < 30s实时消费中健康 —— 无需动作
backlog 持续增长消费跟不上生产查 Worker 错误与接收端时延
DLQ > 0 但在排空瞬时故障正在被自动回灌无需动作
DLQ 持续增长不可处理的文件或接收端宕机检查该死信消息 / 接收端
send-queue backlog 增长接收端慢/不可用，或 max_concurrency 被手动限低查接收端；确认 max_concurrency 未设
